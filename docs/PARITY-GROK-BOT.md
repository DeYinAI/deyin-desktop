# Deyin Bot: parity with Grok Bot

An honest map of Deyin Bot against the product shape recovered from Grok Bot 1.2.3. Where this page and a
claim in the app disagree, this page is the one that is checked: `packages/host-core/test/bot-parity.test.ts`
fails when a recovered field has no answer, when a surface names a file that is not there, or when the tables
below drift from the code. The wider desktop map is [PARITY.md](./PARITY.md).

The recovered contract (enum values, message names and field numbers, tool-name sets) is in
[`docs/rea/grok-bot-1.2.3`](./rea/grok-bot-1.2.3/FINDINGS.md), with how it was obtained. It is interface
metadata only: no Grok Bot source, interface copy or assets are in this repository, and the avatar forms and colors are
drawn by Deyin (the avatar test fails if one shares a name, id, label or value with the recovered palette).

## Reading the status

| Status | Meaning |
| --- | --- |
| Done | Built, wired end to end, and covered by tests that ran here. |
| Foundation | The plumbing exists and is tested against what can be run here, but it has not been run against the real service, host or account it is meant for. The note says which. |
| Deliberately different | Deyin does the job another way on purpose. |
| Not built | Not in Deyin Bot, with the reason. Nothing in the app implies otherwise. |

## What is different on purpose

- **Local first.** A Bot runs on this computer by default. Nothing needs a Cursor, xAI or Deyin account to work.
- **A server the person owns, not our cloud.** A Bot can instead live on an SSH server the person already has. Deyin installs its own engine there (`deyin-bot-engine`) and runs the Bot's routines and chat on it, with the same permissions the app enforces locally. A server Bot has no browser or screen, so the Vault's fill tools and Take over do not apply to it.
- **No teams.** There is one person. `visibility: team` exists so a Bot imported from elsewhere keeps its meaning, but it is refused when set rather than pretended.
- **`isPrimary`** (the Bot that coordinates the others), **`handle`**, **`hostId`** and **`archived`** are Deyin additions to the Bot.
- **Nothing outward happens on its own.** Anything a Bot would post to a public place (the Bot's X account) waits as a draft until the person approves that exact text. A message that arrives from outside is treated as untrusted text, never as an instruction from the person, and a people-facing channel only answers senders on an allow list the person wrote.
- **Avatars** are Deyin's own forms and colors.
- **Outside conversations** are kept per surface and per sender (a Slack thread, a Teams chat, an email address) and handed to one of the Bot's routines; Grok Bot's separate session kinds (`SLACK_DM`, `TEAMS_GROUP_CHAT`, and so on) are not reproduced.

## Known limits of the outward channels

- Slack, Teams, email and X are written to the services' documented shapes and are **not** verified against a real workspace, tenant, mail provider or X account.
- Slack and Teams need a public https address that Deyin does not provide; the person points their own tunnel or proxy at the local port, and the Bot's Connections page shows the exact URL to give the service.
- X mentions are polled every two minutes and each poll reads at most a hundred, so a burst larger than that between polls would be missed.
- Slack's retry header is deliberately not used to drop a delivery: a retry is recognized by its event id, so a message turned away while busy is still taken when Slack tries again.
- The activity list and each conversation's recent history are kept in memory and are empty after a restart. Identical repeats within five minutes are shown once with a count.
- Email arrives as a signed JSON post. The sender is only as trustworthy as that signature and the allow list, since a `From` line can be forged.

## Keeping this current

The tables above are generated from `packages/host-core/test/parity/table.ts`. Change a status there, then:

```bash
pnpm --filter @deyin/host-core exec tsx test/parity/write.ts
pnpm --filter @deyin/host-core test
```

A surface only moves to Done when the test names the files that carry it and its own tests pass. An outward
channel stays Foundation until it has run against the real service.

## Trying it in the real app

Unit tests cannot say that the window, the preload bridge and the main process agree. `scripts/e2e/bot-app-e2e.mjs`
starts the built desktop app (Electron, a throwaway profile, and a small model server on this computer that
answers every chat with `FAKE-REPLY-n`) and checks the Bot product from the outside:

- a fresh profile starts at Welcome and gets past it without an account;
- the product menu offers Code, Bot and Conductor, and choosing Bot switches the whole shell;
- creating a Bot, then a message to it: the model is asked with the Bot's own persona (not the open project's), the
  reply appears, the conversation is saved as the Bot's, and the Bot has its own folder;
- Connections: a webhook is set up with a routine, the key is shown once, a wrong key is refused, a message to the
  address runs the Bot's routine (the model is asked with the message wrapped as untrusted text) and the run completes;
- the hub answers `ok` on this computer only; the Vault page (with its 1Password switch, which saves) and the
  Servers page open; switching to Conductor and back returns to the Bot; after a restart the app reopens in Bot;
- neither the window nor the main process logs an error.

```bash
pnpm --filter @deyin/desktop exec electron-vite build
node scripts/e2e/bot-app-e2e.mjs      # needs a display (WSLg or Xvfb); screenshots go to $TMPDIR/deyin-bot-e2e-shots
```

It never touches an installed Deyin and never reaches the network. It does not cover a real Slack, Teams, X or
1Password account, or a real remote server; those stay Foundation in the tables above.
